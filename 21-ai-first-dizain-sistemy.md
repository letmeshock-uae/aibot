# Топик 21. AI-first дизайн-системы

До сих пор дизайн-системы строились для человека: разработчик открывает документацию, читает описание компонента, смотрит примеры в Storybook, копирует код. Но всё больше UI-кода сегодня пишет не человек, а агент (топики «Вайбкодинг: сайты» и «Вайбкодинг: интерфейсы»), и если дизайн-система «нечитаема» для агента — он начинает придумывать несуществующие свойства компонентов, ставить произвольные отступы вместо токенов и нарушать консистентность быстрее, чем это когда-либо успевал делать человек. AI-first дизайн-система — это система, спроектированная так, чтобы агент так же надёжно понимал её, как человек-разработчик, а лучше — надёжнее.

Важная оговорка на будущее: в этом топике слово «токен» означает **дизайн-токен** — именованное значение стиля (цвет, отступ, радиус), а не «токен» из топиков про LLM (единица измерения текста, см. глоссарий). Это два разных термина с одинаковым названием, которые в этом топике будут встречаться рядом — стоит явно проговорить разницу пользователю, а не оставлять её угадывать по контексту.

## Кейс: Astryx от Meta

Astryx — дизайн-система Meta, реально существующая и активно развивающаяся. Пример ниже описан по публичным материалам на момент подготовки текста и содержит специфичные технические детали — конкретные флаги CLI, названия команд, ссылки на документацию; как и с любым быстро развивающимся инструментом, конкретику стоит сверять с актуальной документацией перед публикацией.

Один из примеров подхода на 2026 год — **Astryx**, open-source дизайн-система Meta на React (компонентная JS-библиотека для интерфейсов) и StyleX (система стилизации от Meta для строгой типизации CSS-свойств компонента), которую компания обкатывала внутри, а затем открыла как «agent-ready» ([astryx.atmeta.com](https://astryx.atmeta.com/)). Она напрямую отвечает на вопрос «как сделать дизайн-систему, которую не будет "галлюцинировать" ИИ-агент», и стоит разобрать её решения подробно, потому что это не абстрактная теория, а работающая практика.

**Предсказуемые имена и конвенции пропсов.** Все компоненты и их свойства называются по строгому единообразному паттерну без синонимов и «красивых» альтернативных названий — это резко снижает вероятность того, что агент придумает несуществующий проп по аналогии с похожим компонентом.

**Машиночитаемая документация вместо прозы.** Вместо того чтобы агент «парсил» текстовую документацию, CLI Astryx отдаёт структурированный JSON-манифест — полный список команд, аргументов, флагов и форматов ответа, по аналогии с OpenAPI-спецификацией (стандартный машиночитаемый способ описать, какие запросы принимает и что возвращает API) для API. Агент читает данные, а не пытается понять маркетинговый текст.

**CLI как единый интерфейс для человека и агента.** Команда `npx @astryxdesign/cli init --features agents` генерирует файл `AGENTS.md` (или аналог под конкретный инструмент, например `.cursorrules` для Cursor) — с индексом компонентов, поведенческими правилами и справочником команд. Дальше агент работает по одному и тому же API, что и разработчик-человек: `astryx component Button`, `astryx template dashboard --skeleton`, `astryx manifest --json`.

**MCP-сервер.** Дизайн-система хостит собственный MCP-сервер (`astryx.atmeta.com/mcp`), к которому может подключиться любой совместимый агент (Claude Code, Cursor и другие) и «вживую» запрашивать компоненты и документацию, не нося весь объём доков в контекстном окне вручную.

**Обязательный трёхшаговый сценарий работы.** Документация буквально учит агента не выдумывать структуру с нуля, а идти по шагам: сначала посмотреть список готовых шаблонов страниц (`astryx template --list`), затем изучить скелет подходящего шаблона (`astryx template <name> --skeleton`), и только потом читать свойства конкретного компонента (`astryx component <Name>`).

**Плотный, а не «дружелюбный» формат вывода.** Флаг `--dense` у каждой команды убирает форматирование, рассчитанное на человеческий глаз, и оставляет максимум информации на минимум токенов — потому что контекстное окно агента является ограниченным и «дорогим» ресурсом, и вежливая многословная документация в нём — потерянное место.

**Явные ограничения и антипаттерны прямо в инструкции для агента.** Сгенерированный `AGENTS.md` содержит не только «что можно», но и жёсткие «нельзя»: не использовать голые `<div>`, не писать инлайн-стили, не подставлять «магические» значения вместо дизайн-токенов.

**Composition hints в самом коде.** Компоненты сопровождаются JSDoc-аннотациями (стандартный формат комментариев прямо в коде, который описывает, как использовать функцию или компонент, и который умеют читать и человек, и инструменты) с примерами правильной композиции — не просто список пропсов, а готовые паттерны их совместного использования, чтобы агент не изобретал сочетания, которые в системе не предусмотрены.

## Общий инструментарий: не только Astryx

Astryx — показательный, но не единственный способ решить задачу. Три конкретных инструмента ниже стоит знать отдельно от конкретного кейса, потому что они применимы к любой дизайн-системе, а не только к готовым agent-ready системам вроде Astryx:

**Storybook и Storybook MCP.** Storybook — давно устоявшийся инструмент, где каждый компонент дизайн-системы живёт как изолированная, документированная «карточка» со всеми своими вариантами и состояниями — исторически он собирался для человека-разработчика, который выбирает нужный компонент глазами. Storybook MCP превращает ту же самую информацию в источник, доступный агенту напрямую по протоколу MCP (топик «Софт»): агент может запросить, какие компоненты вообще есть и какие у них варианты, вместо того чтобы полагаться на то, что помнит о проекте из контекста разговора или придумывать компонент заново. Для команды, у которой уже есть Storybook, это часто более быстрый путь к «agent-ready» состоянию, чем строить собственную CLI-обвязку с нуля, как это сделала Astryx.

**Figma Code Connect.** Отдельная функциональность Figma, которая явно связывает конкретный компонент в Figma-файле с конкретным компонентом в реальном кодовом репозитории — не просто «похожее имя», а прямая, декларативная привязка. Когда агент через Figma MCP (топик «Вайбкодинг: интерфейсы») читает макет, Code Connect подсказывает ему не «нарисуй что-то похожее на эту кнопку», а «здесь используется именно вот этот `Button` из вот этого файла с вот такими пропсами» — тот же принцип «золотых примеров» и «одного источника правды», что и в остальном этом топике, только встроенный прямо в инструмент Figma, а не собранный вручную.

**Claude Cowork.** Более свежий по сравнению с Astryx и Storybook MCP инструмент — агент от Anthropic, ориентированный на совместную работу над проектом (в противовес одиночной CLI-сессии): несколько участников команды и агент работают в общем, разделяемом рабочем пространстве, а не каждый в своей изолированной сессии терминала. Для дизайн-системы это означает, что агент может опираться на общий, актуальный контекст проекта, к которому уже успела прикоснуться вся команда, а не только тот кусок, который вставил в диалог конкретный человек. Как и с любым активно развивающимся продуктом — конкретные возможности и точный синтаксис команд стоит сверять с официальной документацией на момент использования, а не считать текущее описание или примеры ниже исчерпывающими навсегда. Задача, для которой стоит его рассматривать: начать общую рабочую сессию по проекту дизайн-системы, пригласить в неё коллег и убедиться, что агент видит контекст последних изменений, а не только то, что вставил в диалог один конкретный человек.

## Что стоит добавить от себя: соображения для дизайнера, а не только для инженера

Практика Astryx решает в основном инженерную сторону вопроса. Но дизайн-система — это в первую очередь дизайнерский артефакт, и здесь есть несколько соображений, которые стоит явно продумывать именно дизайнеру, а не оставлять на откуп разработчикам:

**Именование — дизайнерское решение, а не только техническое.** Если у компонента есть двусмысленное или «милое» имя вроде `SuperCard` рядом с обычным `Card`, агент рано или поздно перепутает их или смешает пропсы одного с другого. Дизайнеру стоит участвовать в согласовании номенклатуры компонентов на этапе создания библиотеки в Figma — это теперь не только вопрос эстетики нейминга, а вопрос надёжности всей системы под ИИ-агентами.

**Токены как единственный источник правды, синхронизированный, а не задокументированный отдельно.** Мало написать «используйте токены» в гайдлайне — если Figma Variables и токены в коде синхронизируются вручную и расходятся, агент в какой-то момент получит из Figma MCP (топик «Вайбкодинг: интерфейсы») значение, которого уже нет в коде, и наоборот. AI-first подход требует одного машиночитаемого источника (JSON/YAML), из которого генерируются и стили Figma, и токены кода.

**«Золотые примеры» вместо исчерпывающей документации.** Агенты гораздо надёжнее копируют паттерн из одного качественного, полного примера («вот как выглядит правильно собранная страница дашборда»), чем реконструируют его из абстрактного перечисления всех возможных пропсов по отдельности. Дизайн-система выигрывает не от максимально подробных доков, а от небольшого набора канонических, кураторски выверенных «шаблонов страниц» — ровно то, что Astryx и делает через `template --skeleton`, и это стоит закладывать в дизайн-систему с самого начала, а не добавлять постфактум.

**Гардрейлы как линтинг, а не только как текст инструкции.** Агент может проигнорировать написанные в `AGENTS.md` правила, особенно в длинной сессии, где эти инструкции «выпадают» из контекстного окна (топик «Фундамент»). Поэтому правила стоит дублировать в виде автоматической проверки — ESLint/stylelint (программы, которые автоматически проверяют код на соответствие правилам стиля и находят ошибки ещё до запуска) или git-хук (скрипт, который автоматически запускается на определённом шаге git, например перед коммитом, и может его заблокировать) — который блокирует коммит с инлайн-стилями или произвольным хекс-цветом независимо от того, помнит ли агент про правило в моменте.

**Отдельный «агентский» changelog.** Люди читают release notes; агенты — не читают, если их специально не научить. Имеет смысл вести версионированный, структурированный лог breaking changes специально для агентов: «проп `size` переименован в `variant`, старое значение `large` теперь `lg`» — в формате, который можно скормить агенту при апгрейде зависимости, чтобы он сам мигрировал использования, а не сломал полсистемы одним `npm update`.

**QA-петля именно для ИИ-сгенерированного UI.** Раз агент собирает интерфейсы быстро, ревью должно поспевать за этой скоростью: полезен скрипт, который сравнивает финальные стили с токенами и подсвечивает любое «отвязанное» значение (захардкоженный цвет, случайный отступ) для ручной или второй агентской проверки перед мерджем — это прямое продолжение темы из топика «Оценка и критика результатов ИИ», применённое конкретно к дизайн-системе.

## Примеры команд для практики

- «Вот список компонентов моей дизайн-системы (вставить). Проверь имена на двусмысленность — есть ли пары, которые ИИ-агент может перепутать?»
- «Сгенерируй пример AGENTS.md-файла для нашей дизайн-системы: какие правила обязательно включить, чтобы агент не собирал вёрстку на голых div и инлайн-стилях»
- «Опиши, как я мог бы синхронизировать переменные из Figma с токенами в коде, чтобы у обеих сторон был один источник правды»
- «Помоги составить структуру "агентского" changelog для дизайн-системы: какие поля обязательны для каждой записи о breaking change»
- «У нас уже есть Storybook, но нет agent-ready CLI как у Astryx — с чего начать, чтобы агент мог опираться на Storybook напрямую через MCP?»
- «Объясни простыми словами, чем Figma Code Connect отличается от простого совпадения имён компонентов в Figma и в коде»

## Мини-задание

Попросить агента сгенерировать черновик `AGENTS.md` по реальному списку компонентов своей дизайн-системы (или её части) — с индексом компонентов, конвенциями именования и явными «нельзя». Прочитать результат критично: есть ли в нём правила, с которыми лично не согласен, и почему.
