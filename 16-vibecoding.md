# Топик 16. Вайбкодинг: от идеи до продакшен-деплоя

Вайбкодинг — это разработка через естественный язык, когда человек описывает словами, что должно получиться, а ИИ-агент сам пишет, правит и запускает код, показывая результат вживую, без необходимости самому знать синтаксис языка программирования. Раньше вайбкодинг для дизайнера обычно заканчивался на кликабельном прототипе; сегодня, с MCP и производственными агентными CLI, тот же прототип реально довести до живого, задеплоенного продукта с базой данных и авторизацией — это и разбирается во второй половине топика.

Если слова «бэкенд», «эндпоинт» и «схема базы данных» дальше по тексту не расшифровываются — это специально: понятийный разбор вынесен в отдельный топик «Технический фундамент веб-приложения для дизайнера», к нему стоит обратиться до этого топика, если раньше с этим не сталкивался. А если задача — не сразу собирать рабочий код, а сначала спокойно продумать структуру экрана в диалоге, — для этого есть промежуточная ступень в топике «Дизайн-мышление до кода».

## Веб-агенты (не требуют терминала)

v0 и bolt.new хороши для быстрой генерации отдельных экранов и компонентов по описанию или скриншоту дизайна; Lovable и Replit удобны для сборки целого небольшого приложения с базой данных и логикой; Figma Make превращает макет прямо в Figma в рабочий прототип. Отдельно стоит знать про **paper.design** — ИИ-нативный дизайн-инструмент на бесконечном холсте, где интерфейсы и визуалы создаются промптом прямо на канвасе, а не собираются вручную из слоёв, как в классической Figma; для дизайнера это ближе всего к «вайбкодингу самого макета» ещё до того, как он превращается в код — полезная промежуточная ступень между чистой генерацией изображений и полноценной сборкой в v0/bolt.new.

## Терминальные агенты

Claude Code, Codex CLI, Gemini CLI (см. топик «CLI и терминальные ИИ-агенты») — для тех, кто хочет работать с уже существующим, более сложным проектом, глубже влезать в код и видеть все файлы сразу.

Отдельно стоит знать про **Cursor** — это не терминальный агент, а полноценная IDE (редактор кода с окнами и кнопками, форк VS Code) со встроенным ИИ. По задачам он близок к терминальным агентам (видит весь проект, сам редактирует файлы), но работает через привычный визуальный интерфейс, а не через командную строку — поэтому для дизайнера без опыта в терминале это часто более комфортная точка входа в вайбкодинг сложных проектов, чем Claude Code или Codex CLI.

## Примеры команд для веб-агентов

- «Собери одностраничный лендинг для студии йоги: хиро-секция с фото, три блока с преимуществами, форма записи на пробное занятие, светлая цветовая палитра, шрифт без засечек»
- «Вот скриншот моего макета из Figma — сверстай эту страницу адаптивно, сохрани отступы и пропорции как на макете»
- «Добавь на эту страницу тёмную тему, переключаемую кнопкой в правом верхнем углу»
- «Проверь эту форму на доступность: есть ли подписи у полей, работает ли навигация с клавиатуры»

## Примеры команд для терминальных агентов (запускаются из папки проекта)

```
claude "открой проект, найди все места, где используется старый синий цвет бренда, и замени на новый #2D6CDF"
```
```
codex "сделай кнопку 'Купить' липкой (sticky) внизу экрана на мобильной версии"
```
```
gemini -p "сравни макет в файле design-spec.md с текущей вёрсткой и перечисли расхождения"
```

Полезная привычка — начинать сессию вайбкодинга не с самого промпта на постройку, а с мета-промпта из топика «Мета-промптинг»: описать задачу своими словами модели-чату, попросить оформить её в чёткое ТЗ для агента (разделы страницы, компоненты, состояния, adaptive-поведение), и уже этот структурированный текст отдавать в v0/bolt/Claude Code — так агент реже «додумывает» детали не в ту сторону.

## От прототипа к продакшену

Дальше — четыре навыка, которые превращают «красивый прототип» в реальный работающий продукт. Это уже продвинутый уровень, но именно он открывает дизайнеру возможность самостоятельно доводить небольшие проекты (личный сайт, лендинг, MVP-идею) до реального запуска без разработчика.

### Figma MCP: от макета к рабочему коду

Что такое MCP в общем виде и почему это работает точнее, чем скриншот, — разобрано в топике «Софт» (раздел «MCP: как агент подключается к твоим реальным данным»). Здесь — практика конкретно для Figma: MCP-сервер даёт терминальному агенту (например, Claude Code) прямой доступ к реальному файлу в Figma — компонентам, стилям, токенам отступов и цвета — вместо того чтобы агент угадывал вёрстку по скриншоту. Результат получается точнее по пикселям и сразу использует реальные дизайн-токены проекта, а не придуманные заново значения.

Как подключить в общих чертах (конкретные пункты меню стоит сверять с актуальной документацией — они меняются): открыть Figma, включить Dev Mode для нужного файла и в настройках Dev Mode найти пункт про MCP-сервер — он запускает локальный сервер на компьютере; затем в настройках терминального агента (например, у Claude Code это команда `claude mcp add`) указать адрес этого сервера, обычно `http://127.0.0.1` с портом, который показала Figma. После этого агент в этой же папке проекта получает доступ к открытому файлу Figma и может обращаться к нему прямо во время работы.

Пример промпта после подключения Figma MCP:
```
claude "собери компонент Button по дизайну из Figma-файла [ссылка/имя файла], используй действующие цветовые токены и токены отступов из библиотеки, а не произвольные значения"
```

### Авторизация, база данных и UX-полировка

Как только у прототипа появляется реальный пользователь, ему нужны логин и хранение данных:

```
claude "добавь Supabase базу данных для хранения списка пользователей: создай таблицу users с полями email и created_at, подключи форму регистрации к этой таблице"
```
```
claude "добавь авторизацию через email и через Google, страницу логина и защити приватные страницы от неавторизованного доступа"
```

Отдельный шаг — полировка UX и проверка доступности, прежде чем показывать проект кому-либо:
```
codex "прогони по этому прототипу проверку доступности: контрастность текста, alt-тексты у изображений, фокус при навигации с клавиатуры — и почини найденные проблемы"
```

### Платежи и проверка перед продакшеном

Если у продукта есть платная функциональность, платежи почти никогда не пишут с нуля — подключают готовый сервис вроде **Stripe** (подробнее про саму идею — в топике «Технический фундамент»):
```
claude "подключи Stripe для приёма разовых платежей за подписку 'Pro', создай страницу оплаты и обработай успешный/неуспешный результат"
```

Прежде чем показывать это клиенту, стоит проверить, что API-часть действительно работает, а не просто выглядит рабочей в интерфейсе — здесь пригодятся два вспомогательных инструмента:

- **Postman** — приложение, которое позволяет напрямую «постучаться» в эндпоинт API (топик «Технический фундамент») без интерфейса продукта — отправить тестовый запрос и посмотреть, что именно вернул сервер. Полезно, когда непонятно, проблема в интерфейсе или в самом бэкенде.
- **ngrok** — сервис, который даёт временный публичный адрес для проекта, который пока крутится только на локальном компьютере. Часто нужен для проверки вебхуков (уведомлений от Stripe о том, что платёж прошёл) — внешний сервис не может достучаться до `localhost`, а через ngrok может.

Оба инструмента можно попросить агента настроить и объяснить пошагово — не обязательно разбираться в них самостоятельно, достаточно знать, что они существуют и зачем.

### Git-воркфлоу: как агент работает с историей изменений

**Git** — система версий, которая хранит историю изменений кода: кто, что и когда поменял, и позволяет откатиться назад, если что-то сломалось. Терминальные агенты умеют работать с git напрямую, поэтому дизайнеру полезно знать базовые слова: *commit* — сохранённый «снимок» изменений с описанием; *branch* — параллельная версия проекта для экспериментов, не влияющая на основную; *pull request* — предложение слить изменения из branch в основной проект.

```
claude "закоммить текущие изменения с понятным сообщением на английском и создай новую ветку для эксперимента с тёмной темой"
```

### Тестирование и деплой

Перед показом клиенту или запуском стоит попросить агента написать и прогнать автотесты — это программы, которые сами проверяют, что ключевые сценарии (например, регистрация или отправка формы) действительно работают:
```
claude "напиши и запусти автотесты для формы регистрации, покажи, какие проходят, а какие нет, и почини сломанные"
```

Деплой — публикация проекта в интернет по реальному адресу. Vercel — один из самых популярных сервисов для этого, особенно в связке с агентными инструментами:
```
claude "задеплой проект на Vercel и пришли мне ссылку на живую версию"
```

После деплоя проект готов не только к использованию, но и к тому, чтобы попасть в портфолио с живой ссылкой — см. топик «Портфолио: как презентовать проекты с ИИ».

Что делать, когда что-то из этого сломалось, а не заработало с первого раза, — отдельный топик «Чтение и отладка кода агента». А если задача — не просто собрать продукт с помощью ИИ, а встроить ИИ как функцию внутрь самого продукта для его будущих пользователей (чат-помощник, генерация описаний на лету и подобное) — это уже другая задача, разобранная в топике «ИИ как функция внутри прототипа».

## Примеры команд для практики

- «Объясни простыми словами, что такое git commit и branch — как будто я никогда не занимался разработкой»
- «У меня есть готовый макет в Figma и подключённый Figma MCP — с чего начать сборку компонентов, чтобы не переделывать всё заново?»
- «Вот ошибка при деплое на Vercel (вставить текст ошибки) — объясни, что пошло не так, и предложи исправление»
