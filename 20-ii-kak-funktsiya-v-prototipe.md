# Топик 20. ИИ как функция внутри прототипа

Все топики про вайбкодинг до этого момента были про ИИ в руках у того, кто строит продукт: агент пишет код, а сам готовый продукт может быть каким угодно — хоть без единой ИИ-фичи внутри. Этот топик про другое — про то, как встроить ИИ внутрь самого продукта как *функцию для конечного пользователя*: чат-помощник внутри приложения, автоматическая генерация описаний товара, голосовой ввод, распознавание фото. Технически это значит, что готовое приложение само обращается к API нейросети во время работы — не дизайнер один раз воспользовался ИИ при сборке, а продукт использует ИИ на лету, для каждого своего пользователя.

## Чем это отличается от простого вызова ChatGPT

Когда пользователь продукта нажимает «Сгенерировать описание товара», происходит не то же самое, что открыть отдельную вкладку с ChatGPT: приложение само, из своего кода, отправляет запрос к API модели (топик «Модели ИИ», топик «Софт») с уже готовым, заранее продуманным промптом, получает ответ и показывает его прямо в интерфейсе продукта, без единого лишнего клика. Пользователь может вообще не подозревать, какая конкретно модель стоит за кнопкой — для него это просто ещё одна функция приложения.

## Три типовых сценария для дизайнера

- **Текстовый ИИ внутри интерфейса** — автогенерация описаний, подсказки при заполнении формы, суммаризация длинного текста, встроенный чат-помощник. Технически агенту нужно передать: какую модель вызывать, какой system prompt зашить в код (топик «Фундамент» — это тот же system prompt, только теперь пишет его не пользователь чат-бота, а сам продукт), и что показывать, пока ответ ещё не пришёл. Если сценарий не укладывается в один вызов модели, а требует нескольких шагов подряд (например, «сначала разбери запрос пользователя, потом реши, какой из трёх инструментов вызвать, потом оформи ответ») — для этого существуют **graph-фреймворки** (например, LangGraph): способ описать этот многошаговый сценарий не как один большой промпт, а как схему из шагов и переходов между ними, где каждый шаг — отдельный, проверяемый узел. Дизайнеру не обязательно уметь это собрать самому, но полезно знать, что за фразой «у нас сложный ИИ-сценарий с несколькими шагами» у разработчика на схеме обычно и стоит такой граф — и что это не «просто один большой промпт», а управляемая последовательность.
- **Изображения на лету** — генерация аватара, вариаций дизайна, обложки — прямо в потоке работы пользователя, без похода во внешний генератор изображений.
- **Голос и распознавание** — голосовой ввод вместо печати, надиктовка заметки, распознавание объекта на загруженном фото — задействует те же принципы TTS/STT и мультимодальности, что и в топиках «Генерация голоса и аудио» и «Фундамент», только встроенные внутрь продукта, а не как отдельная функция чат-бота.

## Что важно продумать дизайнеру, даже не касаясь кода

- **Состояние ожидания.** Ответ модели приходит не мгновенно — нужен явный индикатор «генерирую», а не замёрзший интерфейс, который выглядит как поломка.
- **Что показать, если модель ошиблась или не ответила.** Это прямое продолжение принципа graceful failure из топика «Принципы дизайна ИИ-продуктов» — нужен понятный fallback, а не пустой экран.
- **Стоимость каждого вызова — не абстракция.** В отличие от личного чата с лимитом сообщений (топик «Тарифы и лимиты»), здесь каждое нажатие кнопки пользователем продукта стоит владельцу продукта реальных денег через API — подробный разбор чуть ниже.
- **Доверие и разметка результата.** Если результат сгенерирован ИИ и показан как есть — стоит явно обозначить это в интерфейсе, а не выдавать за обычный контент продукта (см. топик «Этика, приватность и ограничения», принцип маркировки ИИ-контента).

## Сколько это стоит: токены и юнит-экономика

Когда продукт сам обращается к API модели, а не пользователь открывает чат, платит за это не пользователь напрямую, а владелец продукта — по токенам на входе и выходе (топик «Тарифы и лимиты», глоссарий). Разница с личным чатом принципиальная: там стоимость размазана по месячной подписке и незаметна, а здесь каждый клик по кнопке — конкретная, посчитаемая сумма, которая напрямую влияет на прибыльность продукта.

Простой пример на пальцах: короткий вызов текстовой модели (промпт плюс ответ на пару абзацев) у большинства современных моделей стоит доли цента — сотые или десятые доли цента за одну генерацию. Кажется незаметной суммой, пока не умножить на масштаб: 1000 пользователей, каждый нажимает кнопку «Сгенерировать» в среднем 5 раз в день — это уже 5000 вызовов в день, и при условной цене в полцента за вызов за месяц набегает реальная сумма, которую нужно закладывать в стоимость продукта заранее, а не обнаруживать постфактум в счёте от провайдера. Генерация изображений и особенно видео стоит на порядки дороже одного текстового вызова (топики «Генерация изображений», «Генерация и монтаж видео») — если ИИ-функция продукта генерирует картинки или видео, а не текст, юнит-экономику стоит пересчитывать отдельно, а не полагаться на интуицию с текстовых моделей.

Механика простая и стоит один раз прогнать её на бумаге ещё до того, как агент начнёт писать код:

```
(стоимость одного вызова) × (сколько раз в среднем один пользователь вызывает функцию за период) × (число пользователей) = стоимость ИИ-функции для бизнеса за этот период
```

Дальше это сравнивается с тем, сколько продукт зарабатывает с одного пользователя за тот же период (тот же принцип выбора тарифа, что и в топике «Тарифы и лимиты», только теперь дизайнер на стороне того, кто платит провайдеру, а не пользователя чат-бота). Именно из этого сравнения рождаются практические решения о дизайне: лимит генераций на бесплатном тарифе, платный лимит на дальнейшие, кэширование одинаковых запросов вместо повторной генерации, выбор более дешёвой модели там, где разница в качестве не критична для задачи.

## Как поставить задачу агенту

```
Добавь в форму создания товара кнопку 'Сгенерировать описание с ИИ': по нажатию отправляй название и категорию товара в API [модель], показывай спиннер во время ожидания, вставляй результат в поле описания с возможностью отредактировать вручную, и покажи понятное сообщение об ошибке, если запрос не прошёл
```

## Примеры команд для практики

- «Придумай 3 места в приложении [описать продукт], где ИИ-функция реально решает задачу пользователя, а не добавлена просто чтобы был ИИ»
- «Спроектируй состояние загрузки и состояние ошибки для кнопки "Сгенерировать с ИИ" — что видит пользователь в обоих случаях»
- «Мы планируем разрешить безлимитную генерацию картинок в приложении — посчитай примерно, во что это выльется по стоимости API при 1000 активных пользователей в месяц, и предложи разумный лимит»
- «У нашего продукта тариф $10/мес, ИИ-функция — текстовая генерация, вызывается в среднем 8 раз на пользователя в месяц. Посчитай примерную стоимость API на одного пользователя и скажи, какая доля тарифа уходит на эту функцию»
- «Проверь этот экран с ИИ-функцией на маркировку: понятно ли пользователю, что результат сгенерирован, а не написан человеком»

## Мини-задание

Добавить в любой свой вайбкодинг-прототип одну маленькую ИИ-функцию (кнопка «сгенерировать» для чего-нибудь) — но перед тем как просить агента её реализовать, сначала на бумаге спроектировать состояние ожидания и состояние ошибки, а уже потом отдавать задачу агенту.
