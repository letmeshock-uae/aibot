# Топик 25. Боты и ИИ-ассистенты как продукт

Всё, что было в топиках «Вайбкодинг: сайты» и «Вайбкодинг: интерфейсы», собирает сайты и приложения — продукты, к которым пользователь сам приходит по адресу. Чат-бот в Telegram, WhatsApp или Slack — другая форма продукта: он живёт там, где уже сидит аудитория, не требует установки и открывается тем же самым интерфейсом, в котором человек и так переписывается с друзьями. Для дизайнера это отдельный, вполне реальный формат сдачи результата клиенту — не только лендинг или прототип, а работающий бот, который решает конкретную бизнес-задачу.

## Бизнес-сценарий раньше кода

Первый вопрос перед тем, как открывать вайбкодинг-агента, — не «какой стек использовать», а «какую конкретно задачу решает этот бот». Частые сценарии для бизнеса: бот поддержки, который отвечает на типовые вопросы клиентов до того, как подключится живой человек; бот-квалификатор лидов, который задаёт несколько уточняющих вопросов и передаёт готовую заявку менеджеру; внутренний бот-помощник команды, который ищет ответы в базе знаний компании; образовательный бот, который выдаёт материал порционно (именно так устроен бот, в котором можно читать этот самый текст). Без чёткого сценария бот легко превращается в набор случайных функций без единой цели — тот же принцип, что и в топике «Брифы с ИИ»: сначала описывается задача и пользователь, а не сразу технические детали.

## ИИ как второй пилот, а не единственный мозг бота

Частая ошибка — сделать всю логику бота одним большим ИИ-промптом, который пытается понять любое сообщение пользователя. На практике надёжнее гибридная схема: предсказуемый скелет из кнопок и фиксированных сценариев (меню, разделы, готовые ответы), который должен работать одинаково всегда, и ИИ подключается точечно, там, где реально нужна гибкость: свободный вопрос пользователя, который не укладывается в готовое меню, персонализация ответа под контекст переписки, извлечение сути запроса из длинного сообщения. Это тот же принцип «постепенного наращивания автономности» из топика «UX-паттерны для ИИ-функций», применённый к архитектуре самого бота: не всё сразу отдавать модели, а явно разделить, где бот работает по правилам, а где — думает.

## Python-окружение и зависимости: что нужно знать, не будучи разработчиком

Большинство ботов для Telegram и похожих платформ пишутся на Python — не потому что это единственный вариант, а потому что у него самая большая база готовых библиотек и документации именно для ботов. Вайбкодинг-агент (топик «Технический фундамент») сам установит нужные зависимости и настроит виртуальное окружение (venv — изолированное пространство, где зависимости конкретного проекта не путаются с зависимостями других проектов на том же компьютере), но дизайнеру полезно знать: если агент пишет «активирую виртуальное окружение» или «устанавливаю зависимости из requirements.txt» — это нормальная, ожидаемая часть процесса, а не признак того, что что-то идёт не так.

## Сборка бота: минимальный путь от идеи до первого ответа

1. Зарегистрировать бота у **@BotFather** в Telegram (или аналогичного сервиса на другой платформе) — это даёт токен доступа, уникальный ключ, по которому платформа узнаёт именно этого бота.
2. Попросить агента собрать минимальный скелет: обработчик команды `/start`, главное меню с кнопками, реакция на текстовое сообщение.
3. Подключить ИИ-слой туда, где он реально нужен по сценарию из первого шага — не раньше, чем скелет уже отвечает на команды предсказуемо.
4. Протестировать локально, на своём компьютере, прежде чем думать о постоянном запуске на сервере.

```
claude "собери минимальный Telegram-бот на Python: команда /start показывает приветствие и три кнопки меню, при нажатии на кнопку 'Задать вопрос' бот пересылает следующее сообщение пользователя в Claude API с system prompt 'отвечай только по теме [X], если вопрос не по теме — вежливо откажись' и присылает ответ"
```

## Запуск на сервере: бот должен работать, даже когда компьютер выключен

Сайт из топика «Вайбкодинг: сайты» обычно вызывается по запросу — кто-то открыл ссылку. Бот работает по-другому: он должен постоянно слушать новые сообщения, а значит быть запущенным круглосуточно, а не только пока открыт ноутбук дизайнера. Практические варианты, от простого к более гибкому:

- **Готовый PaaS-хостинг** (Railway, Render, Fly.io и похожие) — самый низкий порог входа: подключается репозиторий с кодом, сервис сам запускает и перезапускает бота при сбое, стоит недорого при небольшой нагрузке.
- **Собственный VPS (виртуальный сервер)** — больше контроля и обычно дешевле при постоянной нагрузке, но требует самостоятельно настроить постоянный процесс (чтобы бот перезапускался сам при падении, а не оставался выключенным до следующего ручного перезапуска) — агента можно попросить настроить это через системные инструменты вроде `systemd` или менеджер процессов `pm2`, не разбираясь в них с нуля самому.
- **Serverless-функция с webhook** — вместо постоянно работающей программы платформа сама «будит» код каждый раз, когда приходит новое сообщение; экономичнее для ботов с редкими сообщениями, но менее предсказуемо по задержке ответа.

Перед тем как отдавать боту токен и любые ключи API на сервере, стоит пройти чек-лист из топика «Безопасность вайбкодинг-проекта» — токен бота даёт полный контроль над ним, и его утечка равносильна утечке пароля.

## ИИ-ассистент внутри бота: практический паттерн

Когда ИИ-слой уже подключён, полезная привычка — не давать ему отвечать вообще на всё подряд, а явно очертить границы: чёткий system prompt о теме, за пределы которой бот не выходит (см. топик «Фундамент»), явный fallback-ответ, если вопрос не по теме или модель не уверена (принцип graceful failure из топика «Принципы дизайна ИИ-продуктов»), и понятная эскалация к живому человеку для сценариев, где ошибка стоит дорого. Бот, который честно говорит «не уверен, давай подключу коллегу», выглядит для пользователя надёжнее, чем бот, который уверенно придумывает ответ.

## Примеры команд для практики

- «Опиши бизнес-сценарий Telegram-бота для студии дизайна: какую одну конкретную задачу он решает для клиентов студии, и какие 3–4 пункта должны быть в его меню»
- «Собери минимальный скелет Telegram-бота на Python с командой /start и одним пунктом меню, который пересылает вопрос пользователя в ИИ с ограниченным system prompt»
- «Сравни Railway, Render и собственный VPS для бота с небольшой нагрузкой (до 100 сообщений в день) — что проще запустить и дешевле держать первые полгода»
- «Придумай понятную формулировку fallback-ответа для бота поддержки, если пользователь спрашивает что-то за пределами темы бота»
