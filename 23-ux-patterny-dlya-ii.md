# Топик 23. UX-паттерны для ИИ-функций

Топик «Принципы дизайна ИИ-продуктов» даёт рамку мышления — Mental Models, Explainability + Trust, Graceful Failure и так далее. Этот топик — уже узнаваемый словарь конкретных интерфейсных решений, в которые эти принципы превращаются на практике. Полезно знать эти паттерны по именам — это тот же смысл, что и с dolly/pan/orbit в топике «Генерация видео»: общий язык с командой ускоряет обсуждение сильнее, чем описание «на пальцах» каждый раз заново.

## Словарь паттернов

**Quiet AI vs Visible AI.** Quiet AI работает незаметно, встроенным улучшением обычного действия — автодополнение, умная сортировка, тихая подсказка — пользователь может вообще не осознавать, что за этим стоит модель. Visible AI — явно выделенная функция («Сгенерировать с ИИ», отдельный чат-помощник), которую пользователь сознательно вызывает. Это дизайнерское решение, а не техническое: чем выше цена ошибки и чем важнее, чтобы пользователь понимал источник результата (принцип Explainability из топика «Принципы дизайна ИИ-продуктов»), тем больше смысла делать ИИ видимым, а не прятать его в фоне.

**Индикатор силы промпта (prompt strength indicator).** Живой индикатор рядом с полем ввода, который подсказывает пользователю ещё до отправки — достаточно ли деталей в запросе, чтобы получить хороший результат, — по аналогии со шкалой сложности пароля при регистрации. Снижает число разочаровывающих генераций «с одной попытки», которые в топике «Фундамент» разобраны как типичная ошибка новичка.

**Модификаторы (modifiers).** Готовые управляемые параметры вместо того, чтобы заставлять пользователя продукта писать текстовый промпт: переключатель тона («короче» / «формальнее»), кнопка «ещё вариант». Это широкая категория — любой элемент управления, который меняет поведение ИИ без слов.

**Precision knobs.** Более узкий, точный подвид модификатора: явный численный или визуальный регулятор («консервативно ↔ смело», ползунок 0–100%), который даёт ощутимый, измеримый контроль над степенью вмешательства ИИ — в отличие от простого переключателя «включено/выключено» или пресета из готового списка, precision knob даёт непрерывный диапазон.

**Task builder.** Вместо пустого поля для промпта — пошаговая структурированная форма, которая помогает собрать сложную задачу по частям (похоже на анатомию промпта из топика «Фундамент», но зашитую прямо в интерфейс продукта, а не оставленную пользователю на откуп). Особенно полезно для пользователей продукта, которые никогда не разбирали, из чего состоит хороший промпт.

**Forced ranking.** Вместо одного ответа — модель выдаёт несколько вариантов и явно просит пользователя выбрать или ранжировать лучший. Это одновременно улучшает непосредственный результат для пользователя и собирает данные о предпочтениях, которые можно использовать для улучшения системы дальше (принцип Data Collection + Evaluation).

**Style lenses.** Заранее заготовленные пресеты стиля/тона, применяемые к результату одним кликом — предметный аналог стиль-гайда из топика «Генерация изображений», только вынесенный в готовый переключатель внутри продукта, а не составляемый каждый раз заново вручную.

**Daemons.** Фоновые мини-процессы ИИ, которые работают без явного запроса пользователя в моменте — например, автоматически готовят черновик ответа на входящее сообщение, пока пользователь ещё читает его. Ключевой дизайнерский вопрос для daemon-паттерна — как обозначить, что что-то уже подготовлено в фоне, не создавая ощущения слежки или потери контроля.

**Верификационные шаги (verification steps) и consensus meter.** Перед тем как результат ИИ применяется необратимо (особенно для agentic-действий — см. ниже), интерфейс явно останавливается и просит подтверждения. Consensus meter — более тонкий инструмент калибровки доверия: визуальный индикатор того, насколько уверенно или согласованно система пришла к этому результату (например, несколько прогонов модели сошлись на одном ответе или разошлись) — чем ниже согласованность, тем очевиднее должна быть просьба проверить результат вручную.

## Один экран, несколько паттернов сразу: пример

Чтобы паттерны не оставались только словами, вот как несколько из них могут выглядеть вместе на одном гипотетическом экране «Сгенерировать email-рассылку с ИИ»: пользователь заполняет **task builder** (тема письма, аудитория, тон — вместо пустого поля промпта), справа от поля темы виден **индикатор силы промпта** («добавь пример прошлой рассылки — результат будет точнее»); после генерации показываются **три варианта через forced ranking** с просьбой выбрать лучший; у выбранного варианта — переключатель **style lenses** («формальнее» / «дружелюбнее») без повторной генерации с нуля; и перед реальной отправкой всей базе подписчиков — обязательный **verification step**: «Проверь текст и подтверди отправку 12 400 адресам» — потому что при цене ошибки «разослать неудачный текст всей базе» это явно Visible AI с обязательным подтверждением, а не Quiet AI, работающий в фоне.

## Agentic UX: когда ИИ-функция сама совершает действия

Отдельный, более сложный случай — не просто «модель сгенерировала контент», а «агент сам выполняет цепочку действий внутри продукта» (переписка со смыслом топика «CLI и терминальные ИИ-агенты», но теперь с точки зрения того, кто это проектирует для конечного пользователя, а не сам этим пользуется). Здесь работает тот же принцип «режимов одобрения», который уже встречался в терминальных агентах, только теперь его нужно спроектировать самому:

- **Постепенное наращивание автономности.** Не давать агенту сразу полный доступ ко всем действиям — начинать с режима, где агент только предлагает план и ничего не делает без подтверждения, и расширять автономию только для узкого класса заведомо безопасных, легко обратимых действий, по мере того как накапливается доверие к конкретному сценарию.
- **Уровни риска и разные пороги подтверждения.** Не все действия агента одинаково опасны: перекрасить кнопку и списать деньги со счёта не должны требовать одинакового уровня подтверждения. Дизайн agentic-функции должен явно классифицировать действия по цене ошибки и назначать порог подтверждения под каждый уровень отдельно, а не единое правило на всё сразу.
- **Guardrails** — жёсткие ограничения того, что агент не может делать вообще, ни при каком запросе пользователя (аналог «нельзя» из AGENTS.md в топике «AI-first дизайн-системы», только теперь это ограничение для агента внутри продукта, а не для агента, который этот продукт собирает).
- **Permissions** — какие именно действия и данные агенту разрешены для конкретного пользователя или роли — тот же принцип авторизации из топика «Технический фундамент», применённый к самому агенту, а не только к человеку.
- **Approval flow** — явный экран «вот что я планирую сделать, подтверди» перед выполнением необратимого или дорогого действия — прямое отражение «режимов одобрения» из терминальных агентов, только теперь спроектированное для конечного пользователя продукта, который может вообще не знать слова «агент».
- **Human-in-the-loop** — осознанное решение держать финальное решение по определённому классу действий за человеком всегда, без опции полной автономии, — не потому что технология не может, а потому что цена ошибки или этическая значимость решения (принцип Accountability) требует этого как принципа продукта, а не временного ограничения.

## Примеры команд для практики

- «Наш продукт даёт ИИ-агенту право самому редактировать данные пользователя. Распиши, какие действия можно доверить полной автономии, а какие обязательно требуют approval flow, и почему»
- «Спроектируй task builder вместо пустого поля промпта для функции "Составить бриф" в нашем продукте — какие шаги и поля нужны, чтобы результат был предсказуемо хорошим»
- «Предложи, где в этом сценарии [описать] уместнее Quiet AI, а где — явно видимая ИИ-функция, и обоснуй разницу»
- «Собери экран, где сочетаются task builder, forced ranking и verification step, для функции [описать] — распиши, что видит пользователь на каждом шаге»
- «Объясни разницу между обычным модификатором (переключатель тона) и precision knob (числовой ползунок) — когда какой уместнее для функции редактирования фото в нашем продукте»
