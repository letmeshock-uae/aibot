# Топик 19. Библиотеки и ресурсы для вайбкодинга

ИИ-агент из топика «Вайбкодинг» пишет код быстро, но по умолчанию часто изобретает своё: рисует иконку из примитивов вместо готовой иконки, лепит наивный `<canvas>`-график вместо нормальной библиотеки, забивает на карту статичной картинкой. Указать в промпте конкретную, проверенную библиотеку — почти всегда быстрее и надёжнее, чем полагаться на то, что агент сам выберет хорошее решение. Этот топик — не исчерпывающий список всего, что есть на рынке, а стартовый набор из категорий и конкретных имён, которые стоит держать под рукой и вставлять прямо в промпт агенту.

## Иконки: Phosphor

**[Phosphor](https://phosphoricons.com/)** — открытая библиотека иконок с несколькими начертаниями (regular, bold, fill, duotone и другие) и единообразной сеткой, которая хорошо ложится в разные стили интерфейса. В промпте агенту достаточно явно назвать библиотеку и нужное начертание: «используй иконки из Phosphor, начертание regular, размер 24px» — вместо того чтобы агент рисовал SVG-иконки сам (получаются неровными по толщине линии и несогласованными между собой).

## Графики и визуализация данных: ECharts

**[Apache ECharts](https://echarts.apache.org/)** — открытая библиотека для графиков и дашбордов: линейные, столбчатые, круговые диаграммы, тепловые карты, графы связей — с готовой анимацией и адаптивностью из коробки. Для дизайнера, который вайбкодит прототип с данными (аналитика, дашборд, отчёт), явное указание «построй график на ECharts» экономит агенту (и пользователю) массу времени по сравнению с ситуацией, когда агент собирает график вручную на `<canvas>` или SVG с нуля.

## Готовые UI-компоненты: shadcn/ui

**[shadcn/ui](https://ui.shadcn.com/)** — набор готовых, стилистически нейтральных UI-компонентов (кнопки, модалки, формы, таблицы) для React, которые не устанавливаются как обычная библиотека, а копируются прямо в код проекта — то есть агент видит и может свободно редактировать сам исходный код компонента, а не работает с ним как с «чёрным ящиком» из `node_modules`. Именно поэтому shadcn/ui стал одним из самых часто выбираемых по умолчанию решений в агентных инструментах (v0, bolt.new, Claude Code и подобных): агенту физически проще и безопаснее менять то, что он может прочитать целиком, чем гадать о поведении скрытой зависимости. Хорошая привычка — так и просить: «собери форму на компонентах shadcn/ui, не изобретай свои».

## Анимация: Framer Motion и GSAP

Codrops (см. ниже) хорош как источник вдохновения, но сам по себе не пишет код — а библиотека анимации нужна, чтобы агент реализовал задуманное надёжно, а не собирал анимацию вручную на голом CSS. **[Framer Motion](https://motion.dev/)** — самая часто выбираемая библиотека анимации для React-проектов: декларативный синтаксис («анимируй это свойство от A до B за столько-то времени»), хорошо ложится на компонентный подход и на анимации появления/исчезновения элементов интерфейса. **[GSAP](https://gsap.com/)** — более взрослый, платформонезависимый инструмент, сильнее в сложных таймлайнах и синхронизации множества анимаций друг с другом (например, анимация, привязанная к скроллу страницы). Для типового прототипа дизайнера обычно достаточно Framer Motion; GSAP стоит называть агенту явно, когда нужен сложный, синхронизированный сценарий, который просто «анимируй это» не описывает.

## ИИ как функция: AI SDK

Если задача — не просто вайбкодить прототип с помощью ИИ, а встроить вызов ИИ-модели внутрь самого продукта (топик «ИИ как функция внутри прототипа»), агенту не обязательно писать интеграцию с API модели с нуля. **[Vercel AI SDK](https://sdk.vercel.ai/)** — самая распространённая библиотека для этого: даёт готовые, проверенные способы отправить запрос к модели, обработать потоковый (постепенно печатающийся) ответ и показать состояние загрузки, не изобретая это заново для каждого проекта. Промпт агенту стоит формулировать так же явно, как и с остальными библиотеками этого топика: «подключи вызов модели через Vercel AI SDK, а не пиши интеграцию с API вручную».

## Карты и геоданные

Готовый визуал карты в прототипе — частый запрос, и здесь важно сразу понимать разницу тарифов, которая иначе сработает как неприятный сюрприз в продакшене:

- **[OpenStreetMap](https://www.openstreetmap.org/) + Leaflet/MapLibre** — полностью бесплатная, открытая карта и открытые библиотеки для её отображения; для прототипа и MVP почти всегда лучший стартовый выбор, потому что не упирается в лимиты и не требует привязки карты.
- **Google Maps API, Mapbox** — качественнее по визуалу и данным (в частности, локально для многих регионов), но оба начинаются с ограниченного бесплатного лимита запросов в месяц, после которого включается оплата — стоит явно проговаривать этот момент клиенту до старта, а не после того, как счёт за API придёт неожиданно.

Промпт агенту стоит формулировать с явным указанием источника: «добавь интерактивную карту на Leaflet с тайлами OpenStreetMap, без платного API-ключа» — иначе агент может по умолчанию подставить Google Maps и незаметно завести проект в платный тариф.

## Вдохновение и обучение фронтенд-анимации: Codrops

**[Codrops](https://tympanus.net/codrops/)** — сайт с туториалами и открытым кодом по фронтенд-анимации, интерактивным эффектам и нестандартной вёрстке; хорош не столько как библиотека для прямого использования, сколько как референс-банк, который можно скормить агенту напрямую: «вот пример эффекта с Codrops (вставить ссылку или код) — адаптируй похожую анимацию появления карточек под мой проект». Полезная привычка при вайбкодинге нестандартного, «вкусного» интерактива — искать референс на Codrops до того, как просить агента придумать анимацию с нуля, а не после.

## Как формулировать такие промпты агенту

Общий принцип для всех категорий этого топика — называть конкретную библиотеку по имени прямо в постановке задачи, а не полагаться на выбор агента по умолчанию:

```
claude "добавь на дашборд график продаж по месяцам на Apache ECharts, иконки статуса — из Phosphor (regular), карту магазинов — на Leaflet с тайлами OpenStreetMap без платного ключа, форму фильтра — на компонентах shadcn/ui"
```

Если библиотека уже используется где-то в проекте, стоит явно попросить агента её переиспользовать, а не подключать вторую похожую: «в проекте уже подключён shadcn/ui — используй его компоненты, не добавляй новую библиотеку для той же задачи».

## Примеры команд для практики

- «Вот скриншот дашборда конкурента с графиками (вставить) — предложи, какие типы графиков ECharts подойдут для похожей структуры данных»
- «Собери набор из 5 иконок статуса заказа (в обработке, отправлен, доставлен, отменён, возврат) из библиотеки Phosphor — начертание duotone»
- «Сравни OpenStreetMap/Leaflet и Google Maps для карты доставки в приложении: что выбрать для MVP без бюджета на API»
- «Вот референс анимации с Codrops (вставить ссылку) — объясни своими словами, что там происходит технически, прежде чем просить агента её повторить»
- «Собери анимацию появления карточек товаров на скролле на GSAP, а не на CSS-переходах — нужна точная синхронизация с положением скролла»
- «Подключи чат-помощника к моему прототипу через Vercel AI SDK, покажи ответ модели по мере печати (стриминг), а не единым куском после полного ответа»

## Мини-задание

Взять один и тот же маленький элемент интерфейса (иконка или график) и попросить агента собрать его дважды: один раз без указания библиотеки, второй раз — явно назвав конкретную библиотеку из этого топика. Сравнить оба результата и время, которое ушло на каждый.
